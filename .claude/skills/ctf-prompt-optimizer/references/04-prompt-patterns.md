# 04 提示词与 Skill 写作模式库

**来源**：Anthropic 提示工程实践（经社区整理为 "Prompt Patterns for Effective Agents"）+
hack-skills 的三层技能架构 + SploitAgent 的 workspace/决策图 + Agent-Skills-Hub 的脚本契约。
本文件是**吸收后的 CTF 特化版**，用于①写本库的 skill；②优化器归化提示词。

---

## 0. 最高优先级原则：Right Altitude（恰到好处的高度）

| 高度 | 表现 | 问题 |
|---|---|---|
| **太低**（过度约束） | 把每步命令写死、把每种情况都列举 | 脆、限制推理、一线发现无法反馈 |
| **太高**（过空） | 「去分析一下」「注意安全」 | 无指导、行为不可预测 |
| **刚好** ✅ | 给**边界与判据**，方法留给执行时判断 | 既可预测又能应变 |

**CTF 落地**：写 skill 或优化提示词时——
- 给：**范围边界、成功标准、停止条件、判据（何时判否/封板）**
- 不给：「必须第 3 步跑这个命令」这类写死的流程
- 例：不写「用 dirsearch 扫出 admin 目录后爆破」，而写「枚举命名路径；
  若发现后台入口，先判认证门类型再决定策略（见 field-notes 02）」

另两条：
- **Minimalism with Completeness**：最小但完整——不是最短，也不是最全。
- **Clarity over Complexity**：具体优于抽象；细节影响模型表现（错别字都会）。

## 1. 推荐的组件顺序（写 skill / 写提示词都适用）

```
① 角色与身份   ② 职责       ③ 上下文与约束   ④ 工作流
⑤ 检查清单     ⑥ 示例       ⑦ 输出格式       ⑧ 边界（DO / DO NOT）
⑨ 自检问题
```

> 对照：`ctf-prompt-optimizer` 的 10 段模板 = 这套顺序的 CTF 特化版；
> `ctf-playbook` = ④ 工作流；`ctf-field-notes` = ③ 上下文 + ⑤ 清单；
> 各 `evals/` = ⑥ 示例。

## 2. 十个模式（每个：干什么 + CTF 例子）

### 模式 1 · 角色与身份
设定专长与视角，让模型调入对口的领域知识与词汇。
```
你是资深安全工程师，专长：Web 应用攻击面、认证与会话、反序列化、SQLi 绕过。
你是逆向分析师，专长：PE/.NET 结构、字符串与常量提取、反编译结果判读。
你是链上研究员，专长：合约角色矩阵、EIP-7702/4337、资金逐跳追踪。
```

### 模式 2 · 明确的职责
「被调用时做什么」——用编号列出，减少歧义。
```
当你接到一个目标时：
1. 判定任务类型与模板族
2. 建立资产表（先建表再收集）
3. 按类型的阶段链执行，每阶段产出证据
4. 结论分级并在封板前自检
```

### 模式 3 · 具体检查清单
把「别忘项」写成可勾选项——防遗漏，也给出统一的评价标准。
```
## Web 目标清单
- [ ] 认证模型：会话 / 签名 / 双因子
- [ ] 授权模型：身份取自会话还是参数？（参数 ⇒ 测 IDOR）
- [ ] 输入面：注入 / 上传 / 反序列化 / 模板
- [ ] 出口：后台入口、回调、导出接口
- [ ] 限速与封禁信号（429/锁定/WAF）
```

### 模式 4 · 少样本示例（3–5 个，覆盖多样场景）
「几个好例子胜过千言万语」。覆盖：正常路径 / 常见错误 / 边界 / 复杂。
> 本库的 `evals/evals.json` 就是这个模式——每条 = 输入 + 期望输出。

### 模式 5 · 输出格式
固定结构 ⇒ 可解析、可比较、易扫读。
> 本库统一：`status / summary / artifacts / details`（脚本）；报告用
> 「结论 → 关键证据 → 技术原理 → 验证方法 → 修复 → 下一步」。

### 模式 6 · 边界（DO / DO NOT）
明确禁止项与鼓励项，防止有害动作并建立质量底线。
```
DO NOT: 越出授权范围 / 对生产系统做写操作 / 把猜测写成结论 / 删无关数据
DO    : 先只读验证 / 标出结论级别 / 写清复现步骤 / 用完回滚并记录
```

### 模式 7 · 思维链（CoT）
复杂判断前显式推理，提升准确率并让过程可审计。
```
判定前先想：<thinking> 这个门是在查库前还是查库后？有无 oracle？</thinking>
```
> 注意：不要为了 CoT 而 CoT——只在真的需要多步推理处加（判族、判否、封板判定）。

### 模式 8 · 上下文与约束
给足背景，模型才能做**有依据**的判断而非泛泛而谈。
```
## 上下文
- 目标：<host>，技术栈：<指纹>
- 已知：<同族结论 / 上次进展>
- 限制：本机无 Java/Node；出网须走代理；目标有 WAF 限速
```

### 模式 9 · 工作流步骤
每步写清：做什么 / 怎么做 / 找什么。
> `ctf-playbook` 的九阶段即此模式；每阶段的 reference 都按
> 「目标 → 检查清单 → 工具 → 证据模板 → 常见误区 → 防守视角」组织。

### 模式 10 · 自检问题（决策点）
在关键分叉处给一组自问，减少草率结论。
```
### 分叉点：该不该继续打？
- 我是否在重复已做过的枚举？（→ 先读记忆）
- 这个卡点是否已有判否结论？（→ 查 field-notes 02）
- 成功标准还成立吗？（→ 若只剩"再试试"，就该封板）
- 这一步是只读还是写入？（→ 写入先列回滚清单）
```

## 3. 三层技能架构（来自 hack-skills 的验证）

成熟的安全 skill 库普遍采用三层：

| 层 | 作用 | 暴露时机 | 本库对应 |
|---|---|---|---|
| **Master Entry** | 全局路由、阶段评估、跨类切换 | 先暴露 | `ctf-prompt-optimizer` |
| **Category Entry** | 按攻击面分流到稳定主题族 | 先暴露 | `ctf-field-notes/references/01` + `families/`、`ctf-playbook` |
| **Deep Topic** | 完整打法与执行细节 | 按需加载 | `families/f01..f13-*.md`、`onchain-ctf/references/*` |

**为什么要分层**：主入口只做**路由与判据**，细节按需加载 —— 这样既省上下文，
又让「新目标、未知攻击面」时有稳定的入口。

## 4. Workspace 与决策图（来自 SploitAgent 的验证）

成熟方案把「一次作业」建模成**一个目录 + 一张决策图**：

```
workspace/
  scope.txt      # 授权边界（硬边界，不在其中不碰）
  plan.md        # 策略
  notes.md       # 运行日志
  findings/      # 确认的问题
```

**决策图（Attack Map）**：把整次作业表示为
`已证明 / 已排除 / 被阻断 / 已跳过` + **每一项的理由**。

> 我们的对应物：`artifacts/<target>/` + `ctf-field-notes/02` 的判否记录 + `03` 的封板报告。
> **可加强处**：把「已排除/被阻断」也显式记成图（现在多写在报告文字里），
> 下次会话一看就知道**哪些路已经走过**。

## 5. 脚本契约（来自 Agent-Skills-Hub 的验证）

本库新脚本（`tools/`）统一遵守：

```
CLI : --input <path> / --output <path> / --format json|md|csv / --dry-run
安全: --scope <file> / --target <x> / --i-have-authorization（非 dry-run 必需）
输出: {status: ok|warning|error, summary, artifacts, details}
退出: 0=正常, 1=警告, 2=发现问题
```

好处：可组合（一个脚本的输出喂给下一个）、可接 CI、**默认安全**（不传授权标志即 dry-run）。

## 6. 蒸馏边界（哪些该吸收，哪些不该）

写 skill 时**只吸收可复用的判断**，不搬运：

| 吸收 ✅ | 不吸收 ❌ |
|---|---|
| 识别指纹、判否结论、攻击面分类 | 具体目标的一次性凭据/私钥 |
| 漏洞类的**手法与判据** | 完整 exploit 代码（除非本地 lab 复现） |
| 工具的**逻辑与参数语义** | 未经验证的工具特性宣传 |
| 检查清单、决策点、表述纪律 | 与本机环境不符的依赖（Java/Node 工具链） |

**来源标注**：吸收自外部时，记下来源与吸收日期，便于回溯（本文件头部即是）。
